# Checkpoints

A dev box is disposable: when it is closed, everything on it is gone. A **checkpoint** is an encrypted snapshot of your workspace,
stored in a **private GitHub repository that you control** (the "state repo"). The next `ddc start` restores the newest checkpoint onto
a fresh box. This is what makes "rent it for a few hours, then throw it away" safe for your work.

> * The state repo must be **private** and owned by you. Checkpoints are encrypted, but they are still your code, history and shell
>   data: never point `state_repo` at a public repository or at a repository that holds anything else.
> * The passphrase that encrypts them (`DDC_BACKUP_PASSPHRASE` in `secrets.env`) is the only key. **If you lose it, every checkpoint is
>   unrecoverable.** Keep a copy in a password manager before you rely on checkpoints.
> * Checkpoints are optional. With `state_repo = ""` nothing is saved, and `ddc stop` refuses to close the dev box unless you pass
>   `--discard-workspace`.

## Setup

1. Choose a name: in `config.toml` set `state_repo = "OWNER/your-private-state-repo"` (your GitHub account or organisation and a new
   repository name).
2. Run `ddc install`. With `gh` logged in it lists what it will do and asks first (`--dry-run` only lists, `--yes` skips the question):
   create that repository as **private** if it does not exist, and add a **write deploy key** (`state_deploy`) to it. It refuses an
   existing repository that holds anything other than a ddc state repo (only branches `main` and `prev`, `main` containing a ddc
   `manifest.json`), because checkpoints replace the branches.
   To do it by hand instead, create an empty private repository and add the public key `keys/state_deploy.pub` as a deploy key with
   write access.
3. Back up `secrets.env`'s `DDC_BACKUP_PASSPHRASE` (generated by `ddc install`, 48 random bytes, URL-safe).
4. `ddc checkpoint` (needs a running dev box) takes one now and verifies it; `ddc verify` re-checks the newest one without taking a new one.

The box talks to the state repo with the deploy key over SSH (host alias `github-state`); your PC verifies checkpoints with your own
GitHub credentials over HTTPS (`git clone`), so `git` must be able to read the private repository from your PC (`gh auth setup-git`
configures git to use your `gh` login).

## When checkpoints are taken

| Trigger | By | Notes |
|---|---|---|
| every `checkpoint_minutes` (15) | agent on the box | skipped when nothing under `/work`, `~/.claude` or the shell files changed |
| idle (`idle_minutes`) or 20 minutes before the runtime limit | agent on the box | a *final* checkpoint, then it asks the PC to close the box |
| `ddc stop`, the TUI's terminate, resize and stop-all | your PC | final checkpoint, verified on the PC **before** anything is closed; if it cannot be verified the box stays up |
| `ddc checkpoint` / TUI Recovery tab `c` | you | manual, then verified |

## What is in a checkpoint

Separate encrypted archives, so one big project does not drag the others along:

| Archive | Contents |
|---|---|
| `ws-<name>` | one per directory under `/work` (your `[[repos]]` and `[[dirs]]`), including `.git`; **excluding** `node_modules`, `.vite`, `.cache`, `.stryker-tmp`, `*.sock` |
| `results` | `/work/results` (logs, benchmark and job output) |
| `claude` | `~/.claude` (session history; **not** the login file `.credentials.json`, shell snapshots, `statsig`, `downloads`) and `~/.claude.json` |
| `config` | `~/.bash_history`, `~/.gitconfig`, `~/.vimrc`, `~/.npmrc` |

Never archived: `~/.config/ddc` (passphrase, deploy keys, lease env), `~/.ssh`, the Claude login file.

**Be aware of what ends up in there.** Anything you typed or pasted on the box can be in `.bash_history`; `.npmrc` may hold a registry
token; Claude Code transcripts and `.claude.json` can contain whatever you showed Claude; files created on the box (an `.env`, say)
are part of the workspace. The archives are encrypted, but they travel through GitHub and anyone who has the passphrase can read them.
CloudDeck's seeder refuses to copy obvious secrets from your PC onto the box; it cannot police what you create there.

## Format

The state repo has two branches, each holding **one root commit** (no history accumulates):

* `main`: the newest checkpoint
* `prev`: the checkpoint before it (appears after the second checkpoint; replaced together with `main`, in one atomic push)

```
manifest.json
archives/ws-my-project.tar.gz.gpg.part000
archives/ws-my-project.tar.gz.gpg.part001
archives/results.tar.gz.gpg.part000
archives/claude.tar.gz.gpg.part000
archives/config.tar.gz.gpg.part000
```

Each archive is `tar` -> `gzip` (level 1) -> `gpg --symmetric --cipher-algo AES256` (passphrase from the file, no further
compression) -> split into **45 MiB parts** (`partNNN`, three digits) so every file stays below GitHub's per-file limits.

`manifest.json`:

```json
{
  "created_at": "2026-01-01T12:00:00Z",
  "reason": "periodic",
  "dseq": "123456789",
  "host": "box-hostname",
  "repos": {"my-project": {"head": "<40-hex commit>", "branch": "main", "dirty": 0, "stashes": 0}},
  "archives": {
    "ws-my-project": {"entries": 1234, "parts": [{"file": "ws-my-project.tar.gz.gpg.part000", "sha256": "<hex>", "bytes": 47185920}]}
  }
}
```

The format is frozen: checkpoints made by earlier releases restore with the current scripts and checkpoints made now restore with
the earlier ones (both directions are covered by tests). Commits are authored as `ddc <ddc@users.noreply.github.com>`.

Very large workspaces make large repositories; GitHub recommends keeping repositories small and may restrict very large ones. Keep
build output and datasets out of `/work` (or in an excluded directory name) if checkpoints become slow.

## Verification on your PC

After a final or manual checkpoint your PC clones the state repo and checks, for every archive: each part's SHA-256 against the
manifest, that it decrypts with your passphrase, and that the tar entry count equals the manifest's count. For a final checkpoint
(`ddc stop`, terminate) it also checks that every directory under `/work` has an archive and that each repo's checkpointed git `HEAD`
equals the box's live `HEAD`. The last three verified
copies are kept (still encrypted) under `<state dir>/checkpoints/`.

What this does **not** prove: that every file's content is identical to the box (counts and `HEAD` are compared, not a content digest),
and it reads each archive into memory, which is slow for very large workspaces. Both are known limitations.

## Restore

**Automatic.** `ddc start` runs `restore.sh` on the new box. It:

1. refuses to continue if the state repo is unreachable or is not a ddc state repo (an unreachable repo is never read as "empty", so a
   re-seed from your PC cannot later overwrite cloud-only work);
2. verifies each part's SHA-256 and each archive's entry count, extracts into a staging directory, checks each repo's `HEAD`
   against the manifest, and only then renames it into place;
3. never overwrites a directory that already exists on the box (use `/opt/ddc/restore.sh --force` on the box to replace one; the old copy
   is moved to `/work/.ddc/replaced/`, not deleted). The Claude and shell-config archives are merged into the home directory and tracked
   by completion markers under `/work/.ddc/archive-complete/`, so an interrupted copy is repeated instead of being mistaken for done;
4. writes the marker `/work/.ddc-restored` only when everything succeeded. Until then checkpoints are refused.

Repos listed in your config but absent from the checkpoint (first start, or a newly added project) are seeded from your PC.

**Manual, on any machine that has `gpg` and `tar`** (for example if your PC is gone and you only kept the passphrase). On Windows use
Git Bash or WSL: PowerShell pipelines are not binary-safe.

```bash
git clone --depth 1 git@github.com:OWNER/your-private-state-repo.git state
printf '%s' 'YOUR-PASSPHRASE' > pass.txt          # delete it afterwards
mkdir restored
cat state/archives/ws-my-project.tar.gz.gpg.part* \
  | gpg --batch --pinentry-mode loopback --passphrase-file pass.txt -d \
  | tar -C restored -xzf -
```

`prev` is the previous checkpoint: `git clone --branch prev ...`.

## What can go wrong

| Situation | What happens | What to do |
|---|---|---|
| State repo unreachable or key rejected | checkpoint and restore fail loudly; `ddc stop` leaves the dev box running and alerts | fix access (deploy key, repo name), then retry; the watchdog also alerts after repeated failures |
| Upload fails | the repo is untouched; the new checkpoint stays on the box (branch `ck-new` in `/var/tmp/ddc-state`) and the next attempt replaces it | retry `ddc checkpoint` |
| Workspace vanished, or a workspace, the Claude state or the shell config lost over half its entries | checkpoint **refuses** ("would lose ws-..."), the previous checkpoint is kept | if intentional: `ddc checkpoint --allow-shrink` or `ddc stop --allow-shrink` |
| A restore was interrupted | checkpoints are refused until it is repeated; no half-extracted directory can look complete | run `/opt/ddc/restore.sh` again (or `ddc start`) |
| Another box checkpointed meanwhile | the second writer **refuses** to overwrite | restore the newest checkpoint, or set `DDC_ADOPT_REMOTE=1` on the box to overwrite on purpose |
| Unreadable files in the workspace | checkpoint fails (it does not silently skip them) | fix permissions; `DDC_CHECKPOINT_IGNORE_UNREADABLE=1` skips them with a warning |
| Wrong passphrase | decryption fails on restore and on PC verification | use the original `secrets.env`; there is no recovery without it |
| The state repo holds something else | checkpoint and restore refuse to touch it | use an empty private repository |
| Checkpoints disabled (`state_repo = ""`) | nothing is saved; `ddc stop` refuses without `--discard-workspace`; the watchdog only alerts | set `state_repo` and run `ddc install` |
| Forced stop (`ddc stop --force --discard-workspace`, or the watchdog's emergency stops after 30 minutes unreachable or a budget stop) | the box is closed even though no final checkpoint verified; no rescue copy is made (`--force` alone is refused for a dev box) | recover from the last periodic checkpoint in the state repo |

Changing `DDC_BACKUP_PASSPHRASE` later means older checkpoints no longer decrypt with the new value: keep the old one until new
checkpoints exist.
